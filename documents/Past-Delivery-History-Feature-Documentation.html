1. Feature Overview

The Past Delivery History feature provides riders on the QuickCommerce platform with a dedicated, paginated view of all their previously completed (or failed) deliveries. Riders can filter by date range and delivery status, and view a complete timeline of each delivery's lifecycle — from assignment through pick-up, transit, and final delivery.

This feature closes the visibility gap that existed after a delivery moved to the Delivered or Failed state, which previously caused those records to silently disappear from the rider's active dashboard. It also introduces the infrastructure for earnings reporting (order totals in INR) and acts as a foundation for future analytics dashboards.

Scope: This document covers all code changes made to implement the Past Delivery History feature, including the database migration that added per-status timestamp columns, the backend service and API endpoint additions, and the Angular frontend component. It also covers the upstream Rider Delivery Status Update feature (commit 955fbcd) on which this feature depends.

6. Database Migration

Migration: AddDeliveryStatusTimestampsMigration

This migration alters the RiderManagement_DeliveryOrder table to add three nullable DateTime2 columns that record the exact UTC timestamp when each delivery milestone was reached.

Column NameData TypeNullablePurpose
PickedUpOnUtcDateTime2YesWhen rider confirmed order pick-up
InTransitOnUtcDateTime2YesWhen rider started transit to customer
DeliveredOnUtcDateTime2YesWhen rider confirmed delivery to customer

The existing AssignedAtUtc column (added in an earlier sprint) already covered the assignment timestamp. Together, all four columns form a complete audit trail of the delivery lifecycle.

Safety: Each column addition is guarded with if (!Schema.Table(...).Column(...).Exists()), making the migration idempotent and safe to apply to environments that may have partially migrated schemas (e.g., CI environments that run nopCommerce with an existing database).

7. Backend — Service & API Changes

DeliveryOrderService: UpdateDeliveryStatusAsync

The new UpdateDeliveryStatusAsync(int orderId, int riderId, DeliveryOrderStatus newStatus) method enforces a forward-only state machine for delivery progression. Allowed transitions are defined in a dictionary:

var allowedTransitions = new Dictionary<DeliveryOrderStatus, DeliveryOrderStatus> { { DeliveryOrderStatus.Assigned, DeliveryOrderStatus.PickedUp }, { DeliveryOrderStatus.PickedUp, DeliveryOrderStatus.InTransit }, { DeliveryOrderStatus.InTransit, DeliveryOrderStatus.Delivered } };

The method also:

  • Validates rider ownership (prevents one rider from updating another's order)
  • Blocks duplicate transitions (idempotency)
  • Blocks updates to already-Delivered orders
  • Records the UTC timestamp for each milestone step

DeliveryOrderService: GetPastDeliveriesAsync

Returns a paginated list of DeliveryOrder records where the status is Delivered (4) or Failed (5), optionally filtered by date range and status:

public async Task<(IList<DeliveryOrder> Items, int TotalCount)> GetPastDeliveriesAsync( int riderId, DateTime? dateFrom, DateTime? dateTo, int? statusId, int pageIndex, int pageSize)

RiderPortalApiController: GET /api/rider/past-deliveries

Authenticates the current rider via the existing nopCommerce customer session cookie (GetAuthenticatedCustomerAsync()), then calls the service layer. The controller enriches each delivery record with:

  • Customer name (from shipping address or billing address fallback)
  • Delivery address (Address1 + City)
  • Order total converted to INR (×83)
  • All four timestamp fields

RiderPortalApiController: PATCH /api/rider/delivery-status

Delegates to UpdateDeliveryStatusAsync(). Additionally, when the new status is Delivered, the corresponding nopCommerce Order record is marked as OrderStatus.Complete. This ties the rider delivery lifecycle directly into the nopCommerce order management system.

Currency note: Order totals are stored in USD by nopCommerce. The current implementation multiplies by a hardcoded factor of 83 to convert to INR. A TODO comment in the code notes this should be replaced with a dynamic exchange-rate lookup.

11. Delivery Status State Machine

StatusIdEnum ValueLabelNext Allowed StatusTimestamp Set
0PendingPendingAssigned (on AcceptOrder)AssignedAtUtc
1AssignedAssignedPickedUpAssignedAtUtc
2PickedUpPicked UpInTransitPickedUpOnUtc
3InTransitOut for DeliveryDeliveredInTransitOnUtc
4DeliveredDeliveredTerminal — no further transitionsDeliveredOnUtc
5FailedFailedTerminal—

State machine enforcement: The backend service rejects any transition that does not follow the sequential order (e.g., attempting to jump from Assigned to Delivered will return 400 Bad Request). This prevents data integrity issues from race conditions or client-side bugs. Already-terminal orders (Delivered, Failed) cannot be updated.

12. Application Impact Analysis

Before This Feature

Before these changes, once a delivery order reached Delivered or Failed status, it disappeared from the rider's view. There was no way for a rider to review their past work, verify earnings, or look up delivery details after the fact.

The DeliveryOrder table did not record the timestamps at which individual status milestones were reached — only the CreatedOnUtc and (after Sprint 2) AssignedAtUtc columns existed. This made it impossible to report delivery duration or pick-up wait times.

The delivery status could not be progressed from the frontend — the UpdateDeliveryStatus endpoint and its backing service method did not exist. Status changes could only be made from the nopCommerce admin panel.

After This Feature

Riders have a dedicated History page accessible via /rider/past-deliveries from their dashboard. They can review all past deliveries with full timeline detail, filter by date and status, and navigate through paginated results.

The database now records a precise UTC timestamp for each of the four delivery milestones. This data is the foundation for future analytics: average delivery time, pick-up delay, geographic performance heatmaps, and earnings breakdowns.

Riders can self-service the entire delivery lifecycle from their mobile portal — progressing from Assigned → Picked Up → In Transit → Delivered without admin intervention. When a delivery is completed, the corresponding nopCommerce order is automatically moved to OrderStatus.Complete.

Performance Considerations

AreaConsiderationMitigation
Pagination Large riders may have thousands of past deliveries Server-side pagination with configurable page size (max 50). Only the requested page is fetched from SQL.
N+1 queries Controller fetches Order + Address for each delivery in a loop Acceptable at current scale (~10 items/page). Future: batch fetch orders and addresses with IN queries.
DB Index Queries filter on RiderId, StatusId, CreatedOnUtc Recommend adding composite index (RiderId, StatusId, CreatedOnUtc DESC) for production.

Security Impact

ControlImplementation
Authentication All rider API endpoints call GetAuthenticatedCustomerAsync() — uses existing nopCommerce session cookie. No new auth surface.
Authorization Past deliveries endpoint fetches the rider record by customer.Id — riders can only see their own history.
Status update ownership UpdateDeliveryStatusAsync() validates that deliveryOrder.RiderId == riderId before allowing any update.
Input validation Date parameters parsed with DateTime.TryParse(); invalid dates are silently ignored (no filter applied). Page size clamped to 1–50.
CSRF PATCH endpoint uses [IgnoreAntiforgeryToken] — acceptable because the Angular SPA uses same-origin credential cookies, not form tokens.
